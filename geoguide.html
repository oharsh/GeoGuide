The Robot That Never Knew Where It Was

A disaster-response rover that follows a line, classifies what it finds, and plots itself on a live map — while having no idea of its own position. Everything spatial happens on a laptop watching from above. Here is how, and why.

01 Premise

What the system actually does

A scale arena has a black line printed on it forming a road network, five locations where a disaster-response scene is printed, and a start box. An overhead camera watches the whole thing.

01

Identify

Before anything moves, one camera frame is thresholded and contoured to find the five printed images. Each is classified by a fine-tuned InceptionV3 into one of five event classes.

02

Prioritise

Events are sorted by severity — Fire first, Combat last — producing the visit order.

03

Drive

For each destination, the host sends a turn-by-turn string over TCP. The robot follows the line and counts junctions.

04

Stop

The robot never decides it has arrived. The camera tracks the ArUco marker on its roof and replies STOP when it is on the target square.

05

Map

Every frame, the robot's nearest arena marker is looked up in a coordinate table and written to a CSV that QGIS polls, animating it on a georeferenced map.

Three pieces cooperate: an ESP32 that can follow a line but has no idea where it is, a laptop that knows exactly where the robot is but cannot steer it, and a socket between them.

02 Thesis

The split-brain design

This is the decision the whole project rests on, and the one to lead with if you get thirty seconds to describe it.

Decision Where does localisation live?
Option A — on the robot
Wheel encoders plus an IMU, dead-reckoning a position estimate; or a camera on the robot doing visual odometry. Standard mobile-robotics practice. Costs encoders, a filter to fuse them, and constant fighting with drift — wheel slip on a smooth arena surface accumulates error fast, and there is no absolute reference to correct against.
Option B — on the overhead camera ← chosen
The camera sees the entire arena at once and reads an ArUco marker glued to the robot's roof. That is an absolute position measurement with no drift, available every frame. The robot needs no encoders, no IMU, no map, and no notion of distance travelled — only "what do I do at the next junction?"
What it buys
The firmware collapses to about 200 lines with three states. All the hard reasoning — classification, prioritisation, arrival detection, mapping — runs on a laptop with Python, OpenCV and TensorFlow available, where it is vastly easier to write and debug.
What it costs
A hard dependency on the camera. Occlusion, a knocked tripod or a WiFi dropout and the robot is blind and unsteerable. The system only works inside one instrumented room — it is not a design that generalises to an unprepared environment.

The clearest expression of this split is that the robot cannot tell when it has arrived. It finishes its route string, announces ALERT, and keeps crawling forward until the host — watching from above — tells it STOP. Arrival is a fact about the world that only the camera can observe.

How to frame this

"I moved every stateful, spatial decision to the machine that could actually observe the state, and left the robot as a dumb actuator." That sentence is the project.

The fragility to name before they find it

Every one of these numbers is specific to one camera mount. Move the tripod and all of them are wrong. There is no homography or fiducial-based re-registration step — the pixel coordinates are the calibration. That's the single biggest limitation of the design, and README.md says so explicitly.

04 Perception

Finding the events

event_detection.py runs once, before the robot moves. It grabs a 1920×1080 frame, crops to the arena, and isolates the printed images with classical CV — no neural network yet.

gray = cv.cvtColor(arena, cv.COLOR_BGR2GRAY)
_, thresholded = cv.threshold(gray, 195, 255, cv.THRESH_BINARY)
contours, _ = cv.findContours(thresholded, cv.RETR_EXTERNAL, cv.CHAIN_APPROX_SIMPLE)

for contour in contours:
    if cv.contourArea(contour) <= 900:
        continue
    x, y, w, h = cv.boundingRect(contour)
    if not (90 <= w < 200 and 90 <= h < 200):
        continue

The size filter is doing real work. The event images are large bright rectangles; the window 90–200 px on each side simultaneously rejects sensor noise from below and the ArUco markers from above — the markers are physically smaller, so a single bound separates two very different things.

Why threshold at all when you have a CNN?

Because classification and localisation are different problems. The CNN answers "what is this image?", not "where are the images?" Running a detector over the full arena would need a detection architecture, a box-annotated dataset, and far more training data. Thresholding exploits a property you control — the images are printed bright on a dark arena — and reduces the problem to five cheap crops.

The repo's own references.md cites an article on object detection vs. image classification with the note "why this project classifies pre-cropped regions rather than running a detector over the whole arena." The trade was made deliberately.

05 Learning

The classifier

training/train_classifier.py is textbook transfer learning:

inception = InceptionV3(input_shape=[224,224,3],
                        weights="imagenet", include_top=False)
for layer in inception.layers:
    layer.trainable = False          # freeze the whole conv base

x = Flatten()(inception.output)
prediction = Dense(5, activation="softmax")(x)

Why freeze everything? The dataset is small — a handful of printed scenes photographed under varying arena light. Fine-tuning the convolutional stack on that little data would overfit immediately. ImageNet features already encode edges, textures and object parts; only the final decision boundary needs learning. One Dense layer, 15 epochs, done.

Augmentation is applied to train only, never to test:

train_datagen = ImageDataGenerator(rescale=1./255, shear_range=0.2,
                                   zoom_range=0.2, horizontal_flip=True)
test_datagen  = ImageDataGenerator(rescale=1./255)

Shear and zoom simulate the camera's viewing angle and height varying between runs. Augmenting the test set would corrupt the evaluation.

A real bug worth knowing about

Training normalises with rescale=1./255, putting pixels in [0, 1]. But inference in event_detection.py calls preprocess_input(x) on raw 0–255 values, which is InceptionV3's own scaling to [−1, 1].

The model is therefore evaluated on a different input distribution than it was trained on. It will still often be right — the features are robust — but accuracy is being left on the table. The fix is to make both paths agree: use preprocess_input in the generator, or rescale=1./255 at inference. This is classic train/serve skew, and being able to name it is worth more than the bug costs.

The class-order coupling

CLASSES in the training script fixes the model's output indices, and EVENT_NAMES in config.py must list them in the identical order. The training file carries a comment saying exactly that. It works today, but it is an implicit contract across two files with no assertion enforcing it — reorder one list and the robot silently drives to the wrong events.

06 Concurrency

Three threads over one camera

control_center.py runs three threads against a single shared frame.

T1

grab_frames

Does nothing but keep the latest cropped frame in a global. Exists so the other two threads always see the same view without fighting over the capture device.

T2

command_center

The mission state machine. Serves the TCP socket, hands out routes in priority order, and decides when to send STOP.

T3

track_robot

Detects every ArUco marker each frame, finds which is nearest the robot, and writes its coordinates to live.csv for QGIS.

The reason grab_frames exists at all is worth understanding: a cv.VideoCapture object is not safe to read() from two threads. Two consumers would interleave and each get half the frames. Funnelling all reads through one producer and publishing the result solves it — a single-slot buffer, the simplest useful concurrency pattern there is.

Where this is under-engineered

Consumers wait for the first frame with a bare spin:

while not isinstance(gframe, np.ndarray):
    pass

That is a busy-wait burning a full core until the first frame lands. A threading.Event would block properly at zero cost. The shared gframe is also written and read with no lock — benign in CPython for a whole-object rebind, but not something to claim as deliberate design.

07 Protocol

The host–robot conversation

Over one TCP socket on port 8002, the two sides speak a four-message protocol. The robot always speaks first after receiving a route.

HOST →

"ISSRF"

A route string. The robot stores it and begins following the line, consuming one character per junction.

← ROBOT

ALERT

"My route string is empty — I'm on the final approach. Watch for me." It keeps line-following while waiting.

HOST →

STOP

Sent when the camera sees the robot's marker within 5 px of the target square. Only now does the robot halt.

← ROBOT

SEND

"Done here, give me the next route." The host replies with the next destination, or the route home if none remain.

← ROBOT

HOME

Sent when the route begins with Q. The host watches for the start square and replies STOP. Mission complete.

Note what is absent: no acknowledgements, no sequence numbers, no timeouts, no checksums. It leans entirely on TCP for ordering and delivery, and on the fact that both ends are in the same room on the same WiFi.

Defensible, but know the limit

For a controlled arena run this is right-sized — adding a reliability layer on top of TCP would be pure ceremony. But it is strictly a happy-path protocol: if a message is lost, both sides block forever waiting for each other. There is no recovery path and no watchdog. Say "right-sized for the environment, not robust to failure" rather than defending it as production-grade.

Why T and F exist

This is the subtle bit. Arriving at a location facing the wrong way makes the next leg's left and right turns come out mirrored. Two solutions exist:

Decision Handling arrival orientation
Option A — correct at run time
Have the robot track its own heading and rewrite subsequent turns when it discovers it's reversed. Requires the robot to maintain global orientation state — precisely the kind of knowledge this design works to keep out of the firmware.
Option B — encode it in the route string ← chosen
Every leg declares which of two orientations the robot must finish in. The robot compares against the head variable it stored at the last node; if they disagree it U-turns and continues. The host pre-computes whole paths knowing exactly which way the robot will be pointing at every step.
else if (roadConfiguration[0] == 'T') {
    if (head == 'T') { roadConfiguration.remove(0,1); }
    else { uTurn(); roadConfiguration.remove(0,1); }
}

A one-character lookahead replaces a heading estimator. That is the split-brain philosophy applied at the level of a single byte.

The routes themselves

ROUTES is a hardcoded 6×6 dictionary — every from/to pair on the arena, written out by hand:

ROUTES = {
  "I": {"A":"IRF",   "B":"IRLRF", "C":"ISSRSF", ...},
  "A": {"B":"FLRF",  "C":"FLSRF", "D":"TRSRF",  ...},
  ...
}

There is no graph search anywhere in this project. No Dijkstra, no A*, no adjacency structure. With six nodes and a fixed arena, all thirty routes were enumerated once by hand. Be straightforward about that if asked — it is a legitimate engineering call at this scale, and claiming a path-planner you did not write is the fastest way to lose an interview.

09 Firmware

The robot's state machine

vanguard.ino is three states and one loop.

StateBehaviourExits when
FOLLOW_LINERead five IR sensors, nudge left or right to stay centredThe three middle sensors read the line simultaneously
NODE_DETECTConsume one route character; go straight, or stop and turn for nodeTurnDelayInstruction complete — returns to FOLLOW_LINE
STOPAll motor pins lowOn command from the host

How a junction is detected

if (sensor.s2 == HIGH && sensor.s3 == HIGH && sensor.s4 == HIGH) {
    currentState = NODE_DETECT;
}

The middle three sensors do double duty. Read individually they keep the robot centred; read together they mean something entirely different — the robot is straddling a crossing line, i.e. a junction. That is the only event in the entire system that advances the route string. No distance, no time, no encoder ticks: one geometric observation from three binary sensors.

The sensors are read as thresholded analogue values, with a per-sensor reference because the IR modules are not identical:

sensors.s1 = read(sensor1Pin, 3500);
sensors.s2 = read(sensor2Pin, 3100);   // note: different threshold
sensors.s3 = read(sensor3Pin, 3500);

Sensor 2's threshold of 3100 against everyone else's 3500 is a hand-tuned compensation for one physically less sensitive module — the kind of detail that only comes from bench work.

10 Control

Line following, and the PID that was thrown away

The controller is bang-bang: read the sensors, nudge in a direction for a fixed number of milliseconds, repeat.

if (s3 == HIGH && s2 == LOW && s4 == LOW) { forward(); delay(turnDelay); }
else if (s2 == HIGH) { left();  delay(turnDelay); }      // 20 ms
else if (s4 == HIGH) { right(); delay(turnDelay); }
// outer sensors caught a rail — bigger correction
else if (s1 == HIGH) { right(); delay(sideTurnDelay); }  // 60 ms

Two correction magnitudes: a 20 ms nudge for small drift detected by the inner sensors, and a 60 ms shove when an outer sensor catches a rail, meaning the robot is badly off. A crude two-level proportional response.

A PID controller was tried first, and abandoned

docs/hardware.md records the attempt:

int position = sensor2Value * 1.34 - sensor4Value * 1;
error = setPoint - position;
myPID.Compute();
out = map(output, 0, 255, -255, 255);
Decision PID vs. bang-bang
Why PID failed here
PID needs a continuous error signal. These are digital IR sensors thresholded to 0 or 1, so "position" could only ever take about three distinct values. The derivative term was differentiating a staircase — mostly noise — and gains tuned on one arena section never generalised to another.
Bang-bang ← chosen
Less elegant, far more repeatable. With a three-level input signal there is nothing for a smarter controller to exploit.
What would have made PID work
Analogue reflectance sensors giving a genuine continuous position estimate — a QTR array read as raw values rather than thresholded booleans. The repo keeps the QTR library documentation for exactly this reason. The controller wasn't the problem; the sensor resolution was.
This is the best story in the project

"I tried the sophisticated thing, understood precisely why it couldn't work with my sensors, and chose the simpler thing on evidence" is a stronger answer than any working PID loop would have been. Have the sensor-resolution explanation ready — that's the part that shows you understood the failure rather than just retreating from it.

The timing constants are the real calibration

nodeTurnDelay is 660 ms — how long a turn runs before line-following resumes. Too short and the robot rejoins the line before clearing the junction and immediately re-detects the same node; too long and it overshoots. hardware.md records that it was raised from 620 ms to 660 ms after the drive batteries were changed — a timing-based open-loop turn is directly coupled to motor voltage.

11 Localisation

ArUco tracking and nearest-marker snapping

ArUco markers are square black-and-white fiducials from the DICT_4X4_250 dictionary — a 4×4 grid of bits with error correction, giving 250 distinguishable IDs. The robot wears id 100; the arena carries lower-numbered markers along the line.

Adaptive thresholding, not plain greyscale

gray_frame = cv.adaptiveThreshold(gray_frame, 255,
    cv.ADAPTIVE_THRESH_GAUSSIAN_C, cv.THRESH_BINARY, 11, 2)
marker_corners, marker_ids, _ = aruco.detectMarkers(gray_frame, MARKER_DICT, ...)

Arena lighting is uneven — brighter under the lamp, dimmer at the edges. A single global threshold loses markers in the dark corners. Adaptive thresholding computes a local threshold per neighbourhood (11×11 here), so each marker is binarised against its own surroundings. The docstring calls this out as "much more robust than raw greyscale under uneven arena lighting," and it's a genuine practical finding.

Position by nearest marker

distances = {mid: distance_between(pos, robot)
             for mid, pos in marker_positions.items()
             if mid != ROBOT_MARKER_ID}
distances = dict(sorted(distances.items(), key=lambda a: a[1]))

The robot's plotted position is not its own pixel coordinate — it is the coordinate of whichever arena marker it is closest to, provided that marker is within 80 px. This quantises position to the marker grid, which is exactly what you want for a map that shows "the robot is at this point on the road network."

The seven STATIC_MARKERS exist purely to fill gaps where the line has no marker nearby. Their positions never change, so they're hardcoded rather than detected — and without them the plotted position visibly jumps between distant markers.

Two defects in this path

Stale positions. distances is declared outside the loop and only recomputed when markers are visible. If detection fails on a frame, the previous frame's ranking is silently reused and the last position is re-written as if fresh.

The centre calculation is not the centre. marker_center() averages the x of two corners and the y of two others. ArUco returns corners as top-left, top-right, bottom-right, bottom-left, but the code names them top_right, top_left, bottom_right. It happens to land near the true centre for an axis-aligned marker and drifts as the marker rotates. Averaging all four corners would be both correct and simpler.

12 Mapping

The live QGIS map

The mechanism is deliberately primitive, and that's why it works.

def write_live_position(ar_id, lat_lon):
    with open(config.LIVE_CSV, "w") as csv_file:
        csv_writer = csv.writer(csv_file)
        csv_writer.writerow(["lat", "lon"])
        csv_writer.writerow(lat_lon[ar_id])

A single-row CSV, rewritten every frame. QGIS loads it as a delimited-text layer with a refresh interval set in Layer Properties, and redraws the point each time it re-reads the file. No plugin, no socket, no database.

01

arena.tif — georeferenced raster

A photo of the arena, georeferenced in QGIS so arena positions map to real latitude/longitude.

02

lat_long.csv — the lookup

Headerless: marker id, latitude, longitude. Read off the georeferenced raster at each marker's physical position. Not committed to the repo.

03

live.csv — the moving point

Overwritten each frame with the current position. QGIS polls it.

So the pipeline is: pixel position → nearest marker id → lat/long from a table → CSV → QGIS layer. There is no coordinate transform in the code at all. The projection work was done once, manually, when the raster was georeferenced and the table was read off it.

If asked "why not compute a homography?"

You could — solve a pixel-to-world transform from four known correspondences and project any pixel to lat/long continuously. It would be more elegant and would survive small camera movements. But the map only needs to show which point on the road network the robot occupies, and marker positions are discrete anyway, so the lookup table delivers the same visible result for a fraction of the work. Know the alternative; defend the choice on requirements.

13 Rationale

Alternatives considered, collected

ProblemAlternativeWhy the chosen route won
LocalisationEncoders + IMU dead reckoningDrift with no absolute reference; overhead ArUco gives a driftless absolute fix every frame
Line controlPIDDigital IR sensors give ~3 position levels; no continuous error signal for PID to act on

ClassificationTrain a CNN from scratchDataset far too small; frozen ImageNet base + one dense layer avoids overfitting
Path planningDijkstra / A* over a graphSix nodes, fixed arena — thirty routes enumerated by hand, no runtime search needed

OrientationRobot tracks its own headingWould push global state into firmware; T/F characters encode it in the route instead

Read down the "why" column and one pattern repeats: exploit what is controlled about the environment instead of solving the general problem. The arena is fixed, the lighting is arranged, the images are printed bright, the camera doesn't move. Every simplification cashes in one of those guarantees.

That is also the honest limitation. This system is excellent inside its arena and does not generalise outside it — and saying so yourself is far stronger than being led to it.

14 Honesty

Gaps and fragilities

1 — Event-to-location mapping is unsafely ordered

identified_labels = {
    chr(i + 65): detected_events[i][1]
    for i in range(len(detected_events)) ... }

This maps the i-th contour found to letter A+i, assuming contours arrive left-to-right. Nothing sorts them. cv.findContours returns contours in an implementation-defined order, and no sort by x-coordinate is applied. Worse, if a location holds no image, every later event shifts one letter left and the robot drives to the wrong squares.

Fix: sort event_regions by bounding-box x, and map to arena letters by position rather than by discovery index.

2 — Train/serve preprocessing mismatch

Covered in §5. rescale=1./255 at training, preprocess_input at inference.

3 — The blank class can never be predicted

EVENT_NAMES has six entries including a blank " ", and the code filters on it. But the model's final layer is Dense(5), so argmax only ever returns 0–4. The blank branch is unreachable; empty locations are handled by the contour filter simply not finding them.

4 — The camera is released while still in use

track_robot calls cap.release() when its window is closed, but grab_frames and command_center are still running against that same capture object.

5 — Busy-wait spin loops

while not isinstance(gframe, np.ndarray): pass appears in both consumer threads.

6 — Stale position on detection failure

Covered in §11 — distances persists across frames.

7 — No failure handling in the protocol

No timeouts, no retries, no watchdog. A dropped message deadlocks both sides.

8 — Everything is calibrated to one physical setup

Pixel coordinates, crop rectangles, turn delays and sensor thresholds are all specific to one camera mount, one battery set and one sensor array. The README says so; that honesty is a feature of the project, not a defect in it.

How to use this section

If asked "what would you fix first?", lead with the contour-ordering bug — it is a genuine correctness issue with a clear fix, and finding it in your own code reads far better than defending code you haven't re-examined.

15 Preparation

Questions to expect

How does the robot know where it is?

It doesn't — deliberately. It has no encoders, no IMU and no map. An overhead camera reads an ArUco marker on its roof and holds the only position estimate in the system. The robot knows just one thing: what to do at the next junction. That split is the central design decision.

How does it know it has arrived?

It doesn't decide that either. When its route string runs out it sends ALERT and keeps line-following. The host compares the robot's marker position against the destination's pixel coordinates with a 5-pixel tolerance and replies STOP. Arrival is observed from above, not inferred on board.

What path-planning algorithm did you use?

None. With six nodes on a fixed arena, all thirty from/to routes are enumerated by hand in a dictionary in config.py. There's no graph structure and no search at runtime. A* would be the answer if the arena were reconfigurable or much larger — at this scale the lookup table is simpler and impossible to get wrong at runtime.

Why does the route string contain T and F?

They encode which of two orientations the robot must finish a leg in. Arriving backwards mirrors the next leg's turns. Rather than have the firmware track global heading, each leg declares its finishing orientation; the robot compares it against the head value stored at the last node and U-turns if they disagree. It replaces a heading estimator with a one-character lookahead.

How is a junction detected?

The three middle IR sensors reading the line simultaneously. Individually they keep the robot centred; together they mean it's straddling a crossing line. That single observation is the only thing that advances the route string — no distance, no timing, no encoder counts.

Why bang-bang control instead of PID?

PID was implemented first and abandoned. It needs a continuous error signal, and thresholded digital IR sensors produce roughly three position levels — the derivative term was differentiating a staircase, and gains never generalised across arena sections. The real constraint was sensor resolution, not the controller: analogue reflectance sensors would have made PID viable.

Why classify crops instead of running object detection?

Detection would need a box-annotated dataset and a detection architecture. The event images are printed bright on a darker arena at known sizes, so a brightness threshold plus a contour size filter (90–200 px) isolates them reliably. That reduces the problem to five cheap crops and lets a small classifier handle the only genuinely hard part — what the picture shows.

Why freeze the InceptionV3 base?

The dataset is small. Fine-tuning the whole convolutional stack would overfit immediately. ImageNet features already capture edges, textures and object parts; only the final decision boundary is task-specific, so a single softmax layer over a frozen base is trained for 15 epochs.

Why adaptive thresholding before ArUco detection?

Arena lighting is uneven — bright under the lamp, dim at the edges. A global threshold loses markers in dark regions. Adaptive thresholding computes a local threshold per 11×11 neighbourhood, so each marker binarises against its own surroundings. It measurably improved detection reliability.

Why three threads?

A VideoCapture can't safely be read from multiple threads — two consumers would interleave and each get half the frames. So one producer thread reads and publishes the latest frame to a global, and the mission state machine and the tracker both consume it. It's a single-slot buffer. Honestly, the wait-for-first-frame is a busy-wait spin that should be a threading.Event.

What's the weakest part of the project?

Two things. Functionally, the event-to-location mapping assumes findContours returns contours left-to-right and never sorts them — if that assumption breaks, or a location is empty, the robot drives to the wrong squares. Architecturally, every coordinate and timing constant is tied to one physical setup: move the camera or change the batteries and it needs re-tuning. There's also a train/serve preprocessing mismatch in the classifier that's quietly costing accuracy.
